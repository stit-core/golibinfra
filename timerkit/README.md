# timerkit

Periodic jobs через fx group. Сервис регистрирует `Job` (имя, интервал,
функция) в группу `timer.job`, а `timerkit.Module` подхватывает все такие job'ы
в `fx.Lifecycle`: на старте приложения запускает каждую по своему тикеру, на
остановке — гасит. Panic внутри job'а перехватывается и логируется, процесс при
этом не падает.

Кит не знает, что делают job'ы, и не хранит их состояние — это тонкая обёртка
над `time.Ticker`, привязанная к жизненному циклу fx.

## Импорт

```go
import "git.stit.tech/stit-core/golibinfra/timerkit"
```

Версия и `go get` — см. [корневой README § Использование в проекте](../README.md).

## Быстрый старт

Job описывается значением `timerkit.Job` и отдаётся во fx-граф как член группы
`timer.job`. Конструктор задачи помечается `fx.ResultTags(...)`:

```go
package cleanup

import (
	"context"
	"time"

	"git.stit.tech/stit-core/golibinfra/timerkit"
	"go.uber.org/fx"
)

func NewCleanupJob(svc *Service) timerkit.Job {
	return timerkit.Job{
		Name:     "expired-sessions-cleanup",
		Interval: 5 * time.Minute,
		Run: func(ctx context.Context) error {
			return svc.PurgeExpiredSessions(ctx)
		},
	}
}

var Module = fx.Module("cleanup",
	fx.Provide(
		NewService,
		fx.Annotate(
			NewCleanupJob,
			fx.ResultTags(`group:"timer.job"`),
		),
	),
)
```

В приложении остаётся подключить `timerkit.Module` рядом с модулем, который
регистрирует job. Логи job'ов идут через `*slog.Logger` — его во fx-граф
провайдит `logkit.Module`:

```go
fx.New(
	logkit.Module,      // provide *slog.Logger (handler-chain logkit)
	timerkit.Module,    // подхватывает все group:"timer.job" в fx.Lifecycle
	cleanup.Module,     // регистрирует одну job в группу
).Run()
```

Job'ов в группе может быть сколько угодно — каждый член `timer.job` крутится в
своей горутине независимо от остальных.

### Жизненный цикл и остановка

`timerkit.Module` вешает в `fx.Lifecycle` один хук:

- **OnStart** — на каждую зарегистрированную `Job` поднимает горутину с
  `time.NewTicker(Job.Interval)`.
- **OnStop** — отменяет общий `context.Context`, разделяемый всеми job'ами.

При остановке приложения отмена контекста размыкает `select` в каждой горутине:
тикер останавливается (`ticker.Stop()`), горутина выходит. Этот же `ctx`
передаётся в `Job.Run` — долгая задача обязана уважать `ctx.Done()`, иначе
shutdown будет ждать её завершения (см. подводные камни).

## Конфигурация

Конфига нет — у кита нет `Config`-структуры и ENV-переменных. Интервал задаётся
в самом `Job.Interval` при регистрации; никаких глобальных настроек кит не
читает.

## Observability

Метрик и спанов кит **не эмитит** и от `telemetry` не зависит. Единственный
сигнал — логи через инжектированный `*slog.Logger`, обе записи уровня error с
контекстом job'а (`ctx` передаётся, так что `trace_id`/`span_id` подхватываются
обработчиком логгера, если они есть в контексте тика — у тикера контекста
запроса нет, поэтому обычно их там не будет):

| Событие | Сообщение | Атрибуты |
| --- | --- | --- |
| `Job.Run` вернул ошибку | `timerkit: job error` | `job` (имя), `error` |
| Panic внутри `Job.Run` | `timerkit: panic in job` | `job` (имя), `panic`, `stack` |

Успешные тики не логируются. Если нужны метрики числа запусков, длительности
или счётчик ошибок — их инструментирует сам `Job.Run` (например, через
`bizmetric`); timerkit их не добавляет.

## API

```go
type Job struct {
	Name     string
	Interval time.Duration
	Run      func(ctx context.Context) error
}
```

| Поле | Роль |
| --- | --- |
| `Name` | Идентификатор задачи в логах (`job`-атрибут). Свободная строка, кит её не валидирует и не требует уникальности. |
| `Interval` | Период тикера. Первый запуск — через `Interval` после старта приложения, не немедленно. |
| `Run` | Тело задачи. Получает общий для всех job'ов `ctx`, отменяемый на shutdown. Возврат ошибки логируется и не прерывает цикл — следующий тик придёт штатно. |

Регистрация — только через fx-группу `timer.job`. Конструктор любого типа,
возвращающий `timerkit.Job`, оборачивается в `fx.Annotate(..., fx.ResultTags(
`group:"timer.job"`))`; `timerkit.Module` собирает все такие значения через
`fx.In` с `group:"timer.job"`. Прямого императивного API («запустить этот job
сейчас») кит не предоставляет — он целиком lifecycle-aware и работает только
внутри `fx.App`.

`timerkit.Module` — `fx.Module("timerkit", fx.Invoke(startJobs))`. Это
`fx.Invoke` (не `fx.Provide`): модуль ничего не отдаёт в граф, а только
навешивает lifecycle-хук, поэтому его достаточно просто подключить в `fx.New`.

## Тестирование

Тесты кита бьют прямо во внутреннюю `runJob` (горутина + тикер), без поднятия
`fx.App`, и проверяют три свойства:

- **Job вызывается периодически.** Job с коротким интервалом запускается в
  горутине, тест ждёт `>= 2` вызовов в пределах дедлайна.
- **Остановка по контексту.** После `cancel()` горутина выходит — тест ждёт
  закрытия `done`-канала.
- **Переживание panic.** Job, паникующий на первом тике, на втором отрабатывает
  штатно — счётчик доходит до `>= 2`, значит цикл не умер.

Свою периодику тестируйте на уровне `Job.Run` — это обычная
`func(ctx) error`, её можно звать напрямую без тикера и проверять эффект.
Зависимость на `time.NewTicker` в timerkit жёсткая (кит не принимает
`clockkit.Clock` и не параметризуется часами), поэтому детерминировать сам
интервал в unit-тесте через clockkit нельзя — для проверки расписания берите
короткие реальные интервалы и опрос с дедлайном, как в тестах кита, а бизнес-логику
тестируйте отдельно от планировщика.

## Инварианты и подводные камни

- **Тег группы — `timer.job`, не `timerkit.job`.** Member-тег в `fx.ResultTags`
  должен совпадать с тем, что собирает модуль: строка ровно `group:"timer.job"`.
  Опечатка не даст ошибки компиляции — job просто молча не попадёт в группу и
  никогда не запустится.
- **Первый запуск — отложенный.** Тикер срабатывает через `Interval` после
  старта, а не сразу. Если задача должна отработать на старте — зовите её
  отдельно (например, в своём `OnStart`-хуке), timerkit eager-прогон не делает.
- **`Run` обязан уважать `ctx`.** Контекст отменяется на shutdown. Долгая
  задача, игнорирующая `ctx.Done()`, не прервётся посреди работы — `OnStop`
  отменяет контекст, но не убивает уже идущий `Run`; зависшая горутина задержит
  остановку приложения.
- **Перекрытие запусков не предотвращается.** Каждый тик зовёт `Run`
  последовательно в рамках одной горутины job'а: пока `Run` не вернулся,
  следующий тик не стартует, но тики, пришедшие во время долгого `Run`,
  схлопываются (`time.Ticker` дропает пропущенные тики, а не копит их).
  Если `Run` стабильно дольше `Interval`, фактическая частота падает до темпа
  самого `Run` — это нормальное поведение тикера, не баг. Параллельных
  экземпляров одного job'а кит не создаёт.
- **Panic в `Run` не валит процесс.** Каждый вызов обёрнут в `recover` —
  паника логируется (`timerkit: panic in job` со `stack`) и job продолжает
  тикать дальше. Это страхует процесс от падения, но скрывает баг в шуме логов:
  не полагайтесь на recover как на штатную обработку ошибок — возвращайте
  `error` из `Run`.
- **Ошибка из `Run` не останавливает job.** Возврат `error` логируется
  (`timerkit: job error`) и цикл продолжается. Backoff, retry-лимита или
  отключения «сломанной» задачи у кита нет — если это нужно, реализуйте внутри
  `Run`.
- **Без `fx` кит не работает.** Регистрация и запуск завязаны на `fx.Lifecycle`
  и group-инъекцию; вне `fx.App` публичного способа запустить `Job` нет
  (`runJob`/`startJobs` неэкспортируемы).
