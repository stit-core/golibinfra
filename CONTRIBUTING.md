# Вклад в golibinfra

Это набор инфраструктурных Go-библиотек («кит'ов») для сервисов stit. Вклад
полезен, когда он делает kit'ы чище, надёжнее или удобнее для консьюмера —
наблюдаемость по умолчанию, минимум зависимостей, никакой продуктовой специфики.

## С чего начать

- Прочитай `README.md` (использование, observability, стабильность API,
  версионирование) и `CLAUDE.md` (карта пакетов, инварианты).
- Каждый kit самодостаточен и подключается независимо; кит с конфигом или ресурсом
  экспортирует `Module` для fx-проводки. Чтобы понять стиль — посмотри соседний kit
  рядом с тем, что правишь.
- У каждого кита — свой `README.md` рядом с кодом (назначение, быстрый старт,
  конфиг, observability, API, инварианты); у сложных китов сверх него каталог
  `docs/`. Это первый и основной источник правды по киту — начни с него.

## Принципы

- **Никакой продуктовой специфики.** Если файл знает про конкретные роли, домены,
  имена сервисов — он не здесь, а в сервис-репо. golibinfra — общая lib.
- **Observability by default.** Новый код эмитит метрики/спаны через
  `internal/otelkit` (глобальные `otel.Meter`/`otel.Tracer`, no-op без провайдера);
  resource attrs и экспорт настраивает потребитель.
- **Минимум зависимостей.** Перед новым import проверь stdlib + уже подключённые
  deps. Каждая новая зависимость в `go.mod` обсуждается отдельно.
- **fx-first.** Кит с конфигом или ресурсом отдаёт `Module`; консьюмер собирает `App`
  из них. `Config` провайдит caller (`fx.Provide(<kit>.NewConfig)`); у конфига есть
  `Validate() error` с sentinel'ом `<kit>.ErrConfig`, который зовут и `NewConfig`,
  и конструкторы — невалидный конфиг валит старт, а не первый запрос.
- **Doc-comment на каждом экспорте** — одна строка, начинается с имени.
  `revive.exported` в гейте закрывает типы, функции, var и const; методы на
  экспортируемом приёмнике линтер не проверяет — их смотрят на ревью. Package-doc
  — 1–3 строки. Тексты ошибок и логов — английские, с префиксом кита.
- **envconfig-теги — часть public API.** Имена полей/тегов публичных конфиг-структур
  менять = breaking change; он допустим в minor-релизе, но обязан быть помечен `!`
  в коммите и описан в аннотации тега (см. `README.md § Версионирование`).
- **Forward-only документация.** Текст описывает текущее состояние, без «было/стало» —
  история живёт в `git log`.

## Форк, issue, PR

- **Issue** — для багов и предложений: что наблюдаешь, как воспроизвести, какой kit
  затронут, ожидаемое поведение.
- **PR** — форкни репозиторий, заведи ветку, открой pull request с понятным описанием
  «зачем». Держи PR сфокусированным; не подмешивай несвязанные правки.
- Менять public конфиг-структуры (имена полей, envconfig-теги, типы) — breaking
  для всех сервисов; такое сначала обсуждается.

## Перед PR

```bash
make tools        # один раз: golangci-lint + govulncheck пиненных версий
make hooks        # один раз: core.hooksPath=.githooks, pre-push гоняет make check
make check        # fmt-check + vet + lint + test-full + build + tidy-check + govulncheck + envdoc-check + plan-check
make test         # быстрый цикл: unit -short -race, без контейнеров
```

Зелёный `make check` — gate пройден. Он гоняет и integration-тесты
(testcontainers), поэтому нужен Docker: без него integration-тест падает, а не
пропускается. Что именно он запускает — в `Makefile` (цели можно вызывать по
отдельности: `make lint`, `make test-full`, …; подмножество пакетов для них —
`PKGS=./<kit>/...`, `check` его не видит); есть ещё `make coverage`,
`make bench`, `make fuzz` и `make test-timing` (timing-тест logkit, вне гейта).

- Новый kit → собственный `README.md` кита (+ `docs/` у сложного), строка-индекс
  в `README.md § Пакеты` и, если нужны test-хелперы, `testkit/<name>test`.
- Тронул конфиг / эмитимые метрики / labels / span-attrs → обнови `README.md`
  (+ `docs/`) соответствующего кита, а endpoint-переменную — ещё и в
  `README.md § Per-concern endpoints`; `make envdoc-check` сверит обе стороны.
- Багфикс → регрессионный тест в том же PR; новый `Module` → fx-тест
  (`fx.ValidateApp`).
- **Conventional Commits** — `<type>(<scope>)?: <subject>`, subject ≤72. Типы:
  `feat`, `fix`, `refactor`, `docs`, `test`, `chore`; breaking — `!` и футер
  `BREAKING CHANGE:`. Пример: `feat(httpkit)!: NewServer принимает ServerOption`.

## Стиль

Спокойно и по делу, без хайпа. Doc-comment на экспортируемых идентификаторах —
обязателен (Go-конвенция: начинается с имени). Комментарии **внутри** функций —
только когда WHY неочевидно, не пересказ кода. Названия и формулировки — как у
соседних пакетов: fx-группа — `<kit>.<thing>` с экспортируемой константой,
проба — `Probe(...)`, test-хелперы — `testkit/<name>test`.
