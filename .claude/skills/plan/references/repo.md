# Профиль репо для /plan — golibinfra

- **Роль:** библиотека. Не форкается: потребители (Go-сервисы, в том числе форки
  `go-backend-template`) тянут модуль по тегу `vX.Y.Z`. Сюда приходят прямым заходом или с задачей
  из сервис-репо (generic-примитив, которого нет в ките). Если вместе с китом нужно менять и
  потребителей, это программа в хабе `<org>/infra`, а здесь — её фаза библиотеки.
- **Гейт перед «готово»:** `make check`; перед тегом — `make gate-clean`.
- **Проверка планов:** `make plan-check` — шаг `make check`, поэтому и pre-push; pre-commit в репо
  нет.
- **Сводка планов:** `make plan-check A=--summary` — строки активных планов и число пунктов
  бэклога; заголовка `== Plan ==` у неё нет (его печатает `make status` сервис-репо).
- **Коммит плана без кода:** `chore(plan): …` — типы коммитов держит хук `commit-msg`
  (CLAUDE.md § Git workflow).
- **Типовые проверки шагов:** `go test -short -race ./<kit>/...` → PASS · `make test-full` → PASS
  (нужен Docker) · `make lint` → 0 issues · `make envdoc-check` → OK · `make check` → зелёный.
- **Handoff:** потребителям — через аннотацию тега (`/release`: «Breaking» по китам — что
  изменилось и как мигрировать). В плане раздел `## Handoff` перечисляет, что потребитель делает
  при обновлении; при релизе это уходит в аннотацию. Накопителя handoff нет: недоставленное при
  закрытии плана — в бэклог или новый план.
- **Разбор падений:** отдельного скилла нет — сначала регрессионный тест, воспроизводящий дефект,
  потом фикс (CLAUDE.md § Границы).
- **До плана выясни:**
  - какие киты затронуты и меняется ли public API — сигнатуры, дефолты, имена метрик,
    envconfig-теги: breaking идёт minor'ом с `!` в коммите и строкой миграции в аннотации тега;
  - нужна ли новая зависимость в `go.mod` — она уезжает в граф каждого потребителя, решение за
    пользователем;
  - каких потребителей это касается и что им придётся сделать;
  - observability нового поведения: метрики, спаны, health-проба, README кита (`make envdoc-check`
    сверяет конфиг с доками);
  - нужен ли testkit-сабпакет; для нового кита — это работа `/add-kit`.
