# Skill: release

Версия golibinfra — git-тег `vX.Y.Z`. Реестр модулей — сам Gitea (`git.stit.tech`);
отдельной сборки/артефакта нет — консьюмеры тянут модуль по тегу. Release notes
живут в аннотации тега (`git tag -a`), а не в файле репозитория.

## Когда применять

- "Релизим vX.Y.Z" / "подними версию golibinfra" / "/release".
- После закрытой задачи и зелёного gate, когда пользователь сказал «пора».

## Когда НЕ применять

- Локальная разработка с одновременной правкой консьюмера → `replace`-директива в
  `go.mod` консьюмера (см. `README.md § Локальная разработка`), не тег.

## Шаги

1. **Gate на чистом дереве.** `make gate-clean` — `make check` (с integration,
   нужен Docker) в worktree от HEAD: ловит незакоммиченные и gitignored-файлы, от
   которых зависит сборка. Красное → не релизим. `make hooks` держит тот же
   `make check` на pre-push.
2. **Версия (semver по форме, политика — `README.md § Версионирование`).**
   Совместимость между minor'ами `v1` не гарантируется: **breaking-изменения идут
   minor'ом** (`vX.Y+1.0`) и обязаны быть перечислены в аннотации тега с шагом
   миграции. Только фиксы без смены публичных сигнатур, дефолтов, имён метрик и
   envconfig-тегов → patch. Major (`/vN` в module path) — только по явному решению
   пользователя: он резервируется на случай, когда потребители перестанут
   обновляться синхронно с библиотекой.
   Список коммитов с прошлого тега:
   `git log $(git describe --tags --abbrev=0)..HEAD --oneline`;
   breaking среди них — `... --oneline | grep '!:'`.
   Спроси у пользователя версию, если неочевидно.
3. **Release notes в аннотации тега.** Обязательные секции: `Breaking` (по китам,
   строкой «что изменилось → как мигрировать»; всё, что требует правки кода или
   тестов потребителя; ни одно breaking не пропущено), `Поведение` (сменившиеся
   дефолты и исходы без смены сигнатур и без правок у потребителя), `Изменения`
   (новое: API, метрики, testkit-сабпакеты, опции), `Гейт` (что гонялось).
   Пуш — гейт человека, делаем по явной просьбе:
   ```bash
   git tag -a vX.Y.Z -F - <<'EOF'
   vX.Y.Z

   Breaking:
   - httpkit: NewServer(cfg, schemes...) → NewServer(cfg, opts...) — схемы через httpkit.WithSecuritySchemes(...)
   - ...

   Поведение:
   - natskit: NATS_MAX_RECONNECTS по умолчанию -1 (бесконечные попытки)
   - ...

   Изменения:
   - testkit/logtest: capture-логгер для тестов потребителя
   - ...

   Гейт: make gate-clean (unit + integration, Docker).
   EOF
   git push origin vX.Y.Z
   ```
4. **Следующий шаг — консьюмеру.** Напечатай блок обновления для `<org>/backend`
   (форк `go-backend-template`) и для `ai-gateway-template` / `amocrm-gateway-template`
   вместе с миграционными пунктами из `Breaking` — только теми, что задевают код
   конкретного консьюмера. Сначала сверь baseline консьюмера (`grep golibinfra go.mod`):
   если он отстаёт больше чем на один тег, миграционные пункты есть в каждой
   промежуточной аннотации — перечисли цепочку, а не только последний шаг
   (`git tag -l --format='%(contents)' <тег>` на каждую промежуточную версию;
   breaking-коммиты отрезка — `git log <baseline>..<тег> --oneline | grep '!:'`):
   ```bash
   go get git.stit.tech/stit-core/golibinfra@vX.Y.Z
   go mod tidy
   make check        # обязательный gate в консьюмере
   ```

## Нет тупика

Скилл всегда заканчивается явным следующим шагом: либо блок `go get` для консьюмера
с миграционными пунктами, либо (если gate красный) — что чинить перед релизом.
