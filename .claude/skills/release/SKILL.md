# Skill: release

Версия golibinfra — git-тег `vX.Y.Z`. Реестр модулей — сам Gitea (`git.stit.tech`);
отдельной сборки/артефакта нет — консьюмеры тянут модуль по тегу.

## Когда применять

- "Релизим vX.Y.Z" / "подними версию golibinfra" / "/release".
- После закрытой задачи и зелёного gate, когда пользователь сказал «пора».

## Когда НЕ применять

- Локальная разработка с одновременной правкой консьюмера → `replace`-директива в
  `go.mod` консьюмера (см. `README.md § Локальная разработка`), не тег.

## Шаги

1. **Gate зелёный.** `golangci-lint run ./...` + `go test -short -race ./...` +
   `go build ./...` — все три. Красное → не релизим.
2. **Версия (semver).** Pre-v1.0.0: **minor может быть breaking**. Breaking change
   (переименование public-полей/тегов конфигов, смена сигнатур, изменение корп
   obs-инвариантов) → bump minor (`v0.X.0`); багфикс/добавление без слома → patch (`v0.X.Y`).
   Спроси у пользователя версию, если неочевидно.
3. **Тег + push** (пуш — гейт человека, делаем по явной просьбе):
   ```bash
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```
4. **Следующий шаг — консьюмеру.** Напечатай блок обновления для `<org>/backend`
   (форк `go-backend-template`):
   ```bash
   go get git.stit.tech/stit-core/golibinfra@vX.Y.Z
   go mod tidy
   make check        # обязательный gate в консьюмере
   ```
5. **Если менялись эмитимые сигналы** (метрики/labels/span-attrs) — напомни обновить
   инвентарь observability на стороне control-plane (`corp-infra-template`: managed —
   инстанс на `*.stit.tech`, self-hosted — форк).

## Нет тупика

Скилл всегда заканчивается явным следующим шагом: либо блок `go get` для консьюмера,
либо (если gate красный) — что чинить перед релизом.
