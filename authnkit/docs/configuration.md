# authnkit — конфигурация

Три публичных конфига: `Argon2idConfig` (параметры хэширования), `JWTConfig`
(секрет, TTL и leeway токенов) и `TOTPConfig` (issuer и окно TOTP). Все —
**part of public API**: имена/типы полей и их envconfig-теги менять = breaking
change; выпускается minor-релизом, помечается `!` в Conventional Commit и строкой
миграции в аннотации тега (см. [корневой README § Версионирование](../../README.md)).

У каждого есть `Validate() error`: нарушение окна → `ErrConfig`. `Validate`
вызывают и конструкторы конфигов из ENV (`NewArgon2idConfig` / `NewJWTConfig` /
`NewTOTPConfig`), и конструкторы примитивов (`NewArgon2idHasher` /
`NewHS256JWT` / `NewTOTP`), поэтому невалидный конфиг валит старт приложения,
а не первый запрос.

RBAC конфига не имеет: `Registry` наполняется кодом через `Register`.

## Argon2idConfig

Параметры Argon2id. Передаются в `NewArgon2idHasher(p)` напрямую либо читаются
из ENV через `NewArgon2idConfig()`.

| Env | Поле | Тип | Default | Назначение |
|---|---|---|---|---|
| `ARGON2_TIME` | `Time` | `uint32` | `3` | Число итераций (passes), окно `1..64`. Растит CPU-стоимость линейно. |
| `ARGON2_MEMORY_KIB` | `Memory` | `uint32` | `65536` | Память на один хэш, в КиБ (`65536` = 64 МиБ), окно `8192..1048576`. Главный рычаг стойкости. |
| `ARGON2_THREADS` | `Threads` | `uint8` | `4` | Параллелизм (lanes), окно `1..16`. Обычно = числу ядер. |
| `ARGON2_KEYLEN` | `KeyLen` | `uint32` | `32` | Длина выходного ключа (хэша) в байтах, `16..128`. |
| `ARGON2_SALTLEN` | `SaltLen` | `uint32` | `16` | Длина случайной соли в байтах, `8..64`. |

Окно значений одно и для `Hash`, и для `Verify` (константы `MinTime`, `MaxTime`,
`MinMemoryKiB`, `MaxMemoryKiB`, `MaxCostKiBPasses`, `MinThreads`, `MaxThreads`,
`MinSaltLen`, `MaxSaltLen`, `MinKeyLen`, `MaxKeyLen`): параметры хэшера вне окна →
`NewArgon2idHasher` возвращает `ErrConfig`; PHC-строка вне окна → `Verify`
возвращает `ErrInvalidHash` до вычисления Argon2.

`MaxCostKiBPasses` ограничивает произведение `t * m`, а не каждый параметр по
отдельности: одна проверка стоит не больше четырёх дефолтных хэшей по CPU и не
больше 768 МиБ по памяти, какой бы ни была строка в хранилище. Из-за него
`ARGON2_MEMORY_KIB` = 1 ГиБ недостижим ни при каком `t` ≥ 1 — практический
потолок памяти 786432 КиБ (при `ARGON2_TIME` = 1).

`KeyLen` и `SaltLen` влияют только на новые хэши: при `Verify` фактическая длина
ключа берётся из самой PHC-строки, а соль — из неё же, поэтому изменение этих
полей не ломает проверку ранее выданных хэшей. `NeedsRehash` сравнивает все пять
параметров строки с параметрами хэшера.

## JWTConfig

Секреты, срок жизни access-токена, leeway и привязка токена к выпускающему (`iss`)
и получателям (`aud`). Передаётся в `NewHS256JWT(cfg, opts...)` напрямую либо
читается из ENV через `NewJWTConfig()`.

| Env | Поле | Тип | Default | Назначение |
|---|---|---|---|---|
| `JWT_SECRET` | `Secret` | `string` | — (`required`) | Общий HMAC-секрет для подписи и проверки HS256. Короче 32 байт → `ErrConfig`. |
| `JWT_ACCESS_TTL` | `AccessTTL` | `time.Duration` | `15m` | TTL для `SignAccess`; `> 0`, иначе `ErrConfig` (и в литерале конфига). |
| `JWT_LEEWAY` | `Leeway` | `time.Duration` | `60s` | Допуск рассинхрона часов при проверке `exp`/`nbf`/`iat` в `Parse`. `0` — без допуска; отрицательный → `ErrConfig`. |
| `JWT_PREVIOUS_SECRET` | `PreviousSecret` | `string` | `""` | Секрет до ротации: подписанные им токены ещё принимаются, новые подписывает `JWT_SECRET`. Пусто — ротации нет; короче 32 байт → `ErrConfig` (§ Ротация секрета). |
| `JWT_ISSUER` | `Issuer` | `string` | `""` | `iss`: `Sign*` проставляет, `Parse*` требует совпадения (`ErrTokenAudience`). Пусто — не пишется и не проверяется. |
| `JWT_AUDIENCE` | `Audience` | `[]string` | — (пусто) | `aud` через запятую: `Sign*` проставляет, `Parse*` требует пересечения (`ErrTokenAudience`). Пусто — не пишется и не проверяется. Пустой элемент списка из ENV отбрасывается, список из одних разделителей (`,`) — `ErrConfig`, в `Config` пустой элемент — `ErrConfig`. |

`Sign(ctx, claims, ttl)` принимает TTL явно — для токенов с нестандартным сроком
(одноразовые ссылки, приглашения); `ttl <= 0` → `ErrConfig`.
`SignAccess` берёт TTL из конфига; дефолты — в тегах (`NewJWTConfig`), порог секрета —
константа `MinSecretLen` (32). Срок refresh — у сессий (`session.Config` ниже), не у JWT.

`iss`/`aud` симметричны: что задано, то проставляется при подписи и требуется при
разборе. Одному сервису на своём секрете они не нужны. Сервисы на **общем**
`JWT_SECRET` без `JWT_AUDIENCE` принимают токены друг друга: токен billing открывает
users — у каждого получателя свой `JWT_AUDIENCE`, у выпускающего — список
получателей (рецепт — [usage.md § Изоляция по iss/aud](usage.md#изоляция-по-issaud)).

### Ротация секрета

1. Выкатить `JWT_SECRET=<новый>` и `JWT_PREVIOUS_SECRET=<прежний>`: новые токены
   подписываются новым секретом, выпущенные прежним проверяются им — никого не
   разлогинивает.
2. Через максимальный срок выпущенных токенов (`JWT_ACCESS_TTL` + `JWT_LEEWAY`, у
   `Sign` — его `ttl`) убрать `JWT_PREVIOUS_SECRET`: подписанных прежним секретом
   токенов больше нет.

Проверка идёт текущим секретом, затем прежним; `kid` в заголовке не нужен.

## TOTPConfig

Передаётся в `NewTOTP(cfg, opts...)` напрямую либо читается из ENV через
`NewTOTPConfig()`.

| Env | Поле | Тип | Default | Назначение |
|---|---|---|---|---|
| `TOTP_ISSUER` | `Issuer` | `string` | — (`required`) | Имя сервиса в otpauth-URL (показывается в authenticator-приложении). Пустой или с `:` / `/` → `ErrConfig`: label URL стал бы неоднозначным. |
| `TOTP_SKEW` | `Skew` | `uint` | `1` | Сколько соседних 30-секундных окон принимается с каждой стороны: `1` → код живёт ~90 с, `0` → только текущее окно. Потолок — `MaxTOTPSkew` (2), выше → `ErrConfig`. |

Период (30 с), число цифр (6) и алгоритм (SHA1) — константы кита (`TOTPPeriod`),
одинаковые в `Generate` и `Verify`; конфигурировать их незачем, authenticator-
приложения ждут именно эти значения.

## session.Config

Сроки сессий refresh (`authnkit/session`). Читается из ENV через
`session.NewConfig()`, передаётся в `pgstore.NewStore` или `pgstore.Module`.

| Env | Поле | Тип | Default | Назначение |
|---|---|---|---|---|
| `SESSION_IDLE_TTL` | `IdleTTL` | `time.Duration` | `168h` | Срок refresh-токена: ротация выдаёт следующий на тот же срок, но не дальше срока сессии (`168h` = 7 дней без входа — сессия истекла). `<= 0` → `session.ErrConfig`. |
| `SESSION_ABSOLUTE_TTL` | `AbsoluteTTL` | `time.Duration` | `720h` | Срок сессии от входа; ротация его не продлевает (`720h` = 30 дней — затем вход заново). Меньше `SESSION_IDLE_TTL` → `session.ErrConfig`. |
| `SESSION_CLEANUP_INTERVAL` | `CleanupInterval` | `time.Duration` | `1h` | Период job'а `authnkit.session.cleanup`, удаляющего сессии с истёкшим абсолютным сроком. `<= 0` → `session.ErrConfig`. |

Нулевой `session.Config` отвергается `Validate`: сессия без срока жизни хуже
упавшего старта.

## Тюнинг стойкости Argon2id

Дефолты (`t=3, m=64 МиБ, p=4`) — разумная отправная точка для интерактивного
логина на сервере общего назначения. Калибровка — под целевое время одного
`Hash` (ориентир — 50–250 мс на проде; меньше — слабо, больше — DoS-поверхность
на всплеске логинов).

- **Главный рычаг — `ARGON2_MEMORY_KIB`.** Память дороже всего для атакующего на
  GPU/ASIC; поднимай её в первую очередь, держа `Time` небольшим.
- `ARGON2_TIME` — добивка, когда память упёрлась в RAM-бюджет инстанса; потолки
  окна (`MaxTime` = 64, `MaxCostKiBPasses` = 786432) на порядок выше любой
  разумной калибровки и существуют ради строк из хранилища, а не ради тюнинга.
- `ARGON2_THREADS` ≈ числу доступных ядер; не превышай, иначе lanes сериализуются.
  Он же задаёт предел одновременных вычислений: `max(1, GOMAXPROCS/ARGON2_THREADS)`,
  поэтому пик памяти хэширования — этот предел × `ARGON2_MEMORY_KIB`.
- Замеряй на целевом железе — `go test -bench` в ките есть
  (`BenchmarkArgon2idHash`/`BenchmarkArgon2idVerify`), снимай число там же, где
  будет крутиться сервис.
- Поднятие параметров безопасно для уже выданных хэшей: они проверятся на старых
  параметрах (зашиты в PHC-строку). Перевыпуск под новую стойкость — на
  следующем успешном логине: `Verify` → `NeedsRehash` → `Hash`; кит не делает
  этого автоматически.
